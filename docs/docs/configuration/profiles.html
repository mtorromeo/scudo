scudo

Profiles

Each TOML section defines a profile. The section name identifies the profile for extend and --profile; it is not a match pattern.

FieldTypeDescription
matchstring or array of stringsGlob(s) or /regex/flags matched against the command name, or against the whole command line when the pattern holds a space; any one is enough. See Match patterns. Absent = the profile never matches a command on its own and is reachable only through extend or --profile.
extendstring or array of stringsProfile(s) applied before this one, left to right; see Combining profiles
delegatetrue, string or array of stringsProfiles whose commands, started from inside this sandbox, run in a sandbox of their own: true for every delegable one, or their names. See Delegating commands
delegableboolWhether a sandbox may have this profile’s commands run under it on its request; inherited through extend (default: false). See Delegating commands
replacearray of stringsFields that replace, instead of adding to, what a same-named profile from a lower-priority config file says; only "match" for now. See Same-named profiles across files
inheritboolWhether this profile adds to a same-named profile from a lower-priority config file (true, the default) or replaces it (false); see Same-named profiles across files
execstringAbsolute path of the binary to execute, bypassing PATH resolution
verboseboolShorthand for log.level = "debug", which among other things prints the full systemd-run command before executing (default: false)
confirmboolPrompt for confirmation before executing (default: false); silently skipped in non-interactive shells
envstring or array of stringsEnvironment variables copied into the sandbox from the environment scudo runs in, by name; see Environment
argstableMaps $arg_* variable names to the flag(s) that fill them; see Command argument variables
varstableVariables naming a directory found by looking up the tree; see Lookup variables
filesystemtableWhich paths the command may write, read, not see or not touch; see Filesystem access
networktableNetwork policy; see Network filtering
dbustableWhat the command gets of the session bus; see Session bus
logtableLevel and destination for scudo’s own output; see Logging
systemdtableUnit properties passed to systemd-run; see below

Every key of the systemd table is passed directly to systemd-run as -p Key=value. Use the exact systemd unit property names (PascalCase). Values can be strings, booleans (true/false → yes/no), integers, or arrays. Write it either as a sub-table header ([curl.systemd]) or with dotted keys (systemd.MemoryMax = "256M").

The command starts in the current directory, unless WorkingDirectory is set (in the table or with -P): then systemd-run is not given -d and the property decides.

Any other key is a typo and scudo says so instead of ignoring it.

Environment

The command does not inherit the environment it is started from: systemd-run gives the unit the service manager’s environment (systemctl --user show-environment) and nothing of the shell’s. So a variable set by direnv, or exported in the terminal, is missing inside the sandbox unless a profile names it in env:

[npx]
match = "npx"
env = ["SENTRY_ACCESS_TOKEN", "NODE_OPTIONS"]

--env (-E) does the same for one run, adding to what the profiles name:

scudo -E SENTRY_ACCESS_TOKEN,NODE_OPTIONS npx @sentry/wizard

Each name is passed on with its value at the time scudo runs. A variable that is not set is left out rather than set empty, so a profile shared by several projects can name what only some of them define. env lists add up across combined profiles like any other list.

Only the names appear on the systemd-run command line that scudo prints, but the values become properties of the unit: while the command runs, systemctl --user show on the unit shows them to your own user. systemd.Environment = ["NAME=value"] sets a fixed value instead, and $NAME expands there as in any other value.

Example

The bases here are those of the recommended configuration, cut down to what the example needs.

# The project a command runs in: the closest directory holding a `.git`
[scudo]
vars.PROJECT_DIR = { lookup = ".git", fallback = "cwd" }

# Base profiles — no `match`, so they are never matched directly, only used via extend
[sandbox]
filesystem.read = ["/", "$XDG_RUNTIME_DIR/scudo/shims"]
filesystem.hide = ["$HOME", "$XDG_RUNTIME_DIR"]
filesystem.write = ["/tmp", "$HOME/.cache"]
systemd.PrivateTmp = true

[git-project]
extend = "sandbox"
filesystem.write = ["$PROJECT_DIR"]

# curl: extends the base sandbox
[curl]
match = "curl"
extend = "sandbox"
systemd.MemoryMax = "256M"

# claude: works on the project it is started in, plus any --add-dir
[claude]
match = "claude"
extend = "git-project"
args.add_dir = { flags = "--add-dir", greedy = true }
filesystem.read = ["$HOME/.gitconfig", "$arg_add_dir"]
filesystem.write = ["$HOME/.claude", "$HOME/.claude.json"]
network.dest.allow = ["*.anthropic.com"]

# code: VS Code and its variants
[code]
match = ["code", "code-oss", "codium", "vscode"]
extend = "git-project"
filesystem.write = [
  "/proc",
  "/dev/shm",
  "/dev/dri",
  "$HOME/.vscode",
  "$HOME/.vscode-oss",
  "$HOME/.config/Code",
  "$HOME/.config/Code - OSS",
]
# The display: the one socket of the session's an editor needs, given back alone.
filesystem.read = ["$XDG_RUNTIME_DIR/${WAYLAND_DISPLAY:-wayland-0}"]
# The launcher leaves the editor running and exits: keep the unit until it is gone.
systemd.ExitType = "cgroup"
dbus.talk = [
  "org.freedesktop.secrets",
  "org.freedesktop.Notifications",
  "org.freedesktop.portal.*",
]
dbus.own = ["com.visualstudio.code.*"]

# npm: the npm cache, and the project
[npm]
match = "npm"
extend = "git-project"
filesystem.write = ["$HOME/.npm"]

[pnpm]
match = "pnpm"
extend = "npm"
filesystem.write = ["$HOME/.pnpm-store"]

Every list adds to the ones it inherits: pnpm can write ~/.npm, the project and ~/.pnpm-store, and read everything sandbox lets it read.
